Odoo is a strong ERP with features for running most of a business, but analyzing data isn't one of them, especially once tables get large. You could say that's unfair: there are community modules that add reporting. In practice, installing them is too much for non-technical staff, and someone has to maintain them. That's a heavy burden when the tech team is small and already stretched, which is exactly where I was.

Odoo does have a capable JSON API for pulling raw data. I started writing Python scripts against it to turn billing and sales data into simple reports. After a few trials the reports proved useful, so I focused first on something for the sales team.

  <ArchDiagram slot="stage" diagram={dataPipeline} title="Odoo to dashboards" plate="Fig. 4.1" caption="Tap or hover a component for details." />

  <Step focus="odoo,lambda,ssm" show="odoo,lambda,ssm">
    **Basic reporting.** I needed somewhere to run short scripts on a schedule with as little upkeep as possible. A **Lambda** function was the natural fit, with the Odoo API key kept in **Parameter Store**.
  </Step>

  <Step focus="schedule,lambda,sns" show="schedule,sns,team">
    **Expanding it.** If the first report proved useful, the approach had to scale. I wrote a **Terraform module** that wires up a Lambda function, an **SNS** topic and an **EventBridge Scheduler** rule: a repeatable template, not a one-off script. Then I stamped it out for every Odoo table worth reporting on, such as pending quotations and sales analysis.
  </Step>

  <Step focus="sns,team">
    Two things became clear after a few of these, refined with the sales team's feedback. There's a limit to how many report emails people read before they start ignoring them. And what the business really needed was a place to *explore* the data, not just receive it.
  </Step>

  <Step focus="lambda,s3,athena" show="s3,athena">
    **The platform.** The Lambdas now parse the extracted data, trim the fields nobody uses, and write it to **S3**, partitioned by date. **Athena** runs SQL directly over those files, with no servers to manage.
  </Step>

  <Step focus="athena,metabase,rds,team" show="metabase,rds">
    For the people side I chose **Metabase**: easy to read, self-service dashboards, flexible queries, and a free self-hosted version. It runs as a container on the **ECS** cluster from the [ECS delivery project](../ecs-delivery/), with **RDS** for its own metadata, and it queries S3 through Athena.
  </Step>

  <Step focus="ci,lambda" show="ci">
    **Automating deployment.** Zipping and uploading code by hand didn't survive the number of functions. Each Lambda got its own **GitHub Actions** pipeline that runs only when its directory changes, so updating the sales report never redeploys the quotations one.
  </Step>
</Scrolly>

## The pipeline, in order

1. A Lambda function extracts data from Odoo.
2. The data is parsed and trimmed of unneeded fields.
3. It's uploaded to S3, partitioned by date.
4. Metabase queries the S3 data through Athena.
5. Metabase's BI layer turns raw rows into something people can explore.

## What it changed

The team can now query the full dataset with SQL and build its own dashboards, without waiting for me to write a report.

<Callout>
  It's a pattern I see a lot: the "good enough" reporting that ships with a system stops being good enough as soon as people actually start using their data.
</Callout>
