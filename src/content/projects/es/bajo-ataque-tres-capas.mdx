Que un servidor se caiga de golpe es la pesadilla de cualquier desarrollador, y así empieza esta historia. Una tarde el servidor se cayó sin aviso. Tenía Nginx como proxy inverso delante de un backend en PHP con Laravel, una configuración que hasta entonces había sido estable.

    Para que la próxima vez nos enteráramos antes que los usuarios: una **alarma de CloudWatch** sobre la CPU de la instancia, conectada a **SNS** para que el equipo recibiera el aviso al instante.

    Quitar el estado significaba sacarlo del servidor. La base de datos MySQL pasó a **Amazon RDS**. Las imágenes de usuarios y demás archivos estáticos pasaron a **S3**. A partir de ahí, cualquier instancia podía atender cualquier petición.

Construí esa AMI desde una instancia conectada a RDS, con los procedimientos de MySQL configurados y los datos cargados. Las versiones nuevas siguen el mismo camino: AMI nueva, nueva versión del launch template, instance refresh.
  </Step>

## Terraform, a propósito

Una mejora a dos capas habría sido la opción directa. Vi el incidente como una oportunidad para aprender bien **infraestructura como código**, incluso en un proyecto freelance. Poder desplegar y destruir todo el entorno cuando haga falta lo mantiene limpio y revisable.

El estado vive en un **backend en S3**, así que se guarda en remoto y de forma consistente para cualquiera que trabaje en él. Validé la configuración desplegando primero los cimientos: VPC, subredes y security groups.

También añadí **Checkov** para escanear el plan en busca de errores de seguridad y cumplimiento antes de que nada llegara a AWS:

```bash
python3 -m venv .env
source .env/bin/activate
pip3 install checkov
```

```bash
#!/bin/bash
terraform plan -out tf.plan
terraform show -json tf.plan | jq > tf.json
checkov -f tf.json
```

## Cómo se publica una versión nueva

1. El equipo de desarrollo crea una AMI nueva desde el servidor de staging cuando las funcionalidades están listas.
2. La AMI nueva entra en el launch template, que crea una nueva versión de la plantilla.
3. Un instance refresh, desde la consola o la CLI, reemplaza las instancias con una estrategia **progresiva** que mantiene al menos un 50 % sano en todo momento.

Sin caídas, y la capacidad sigue a la demanda mediante target tracking sobre la CPU media.

## Lo que haría después

- **Seguridad:** AWS WAF delante del balanceador, AWS Shield contra DDoS y MFA en todas las cuentas.
- **Automatización:** un pipeline de CI/CD para los despliegues y Terraform cubriendo todos los componentes.
- **Observabilidad:** logs centralizados y trazas de peticiones con AWS X-Ray.
- **Costos:** capacidad reservada para la base y revisiones periódicas de tamaño.
